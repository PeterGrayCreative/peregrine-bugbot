# Experimental prediction CLI bridge — zero-provider checkpoint

This additive bridge reuses the accepted `ccad8c40…` runtime, authenticated
four-tool reader, existing container/sidecar supervisor, whole-attempt deadline,
terminal parser and prospective CLI batch accounting. Production routing and
the preceding R4 freeze are unchanged. Independent review is still required.

## Exact scope and authority

The bridge authenticates the preceding R4 freeze and reconstructs its scientific
inputs, then separately seals the additive bridge source. Each one-use,
nonserializable capability binds run, freeze, package, canary, source, policy,
purpose, slot, prompt, mount, raw scope and requested Sol/high CLI route.
The operator-only issuer requires explicit permission and gate-evidence hashes;
these are assertions by the trusted operator, not authentication inferred from
JSON or from a hash alone. Review attempts additionally require a separately
reviewed canary receipt and follow the fixed serial batch. Preparation never
issues permission. A canary cannot consume a review slot.

One ephemeral CLI session receives an empty checkout and only the review schema
when reviewing. Both arms retain equal raw source scope; Peregrine instructions
exist only in the registered arm prompt, not ambient filesystem resources.
The exact command uses the scoped `source_read` endpoint with `list_tree`,
`read_file`, `search_text` and literal `read_link`. It disables shell/unified
execution, multi-agent delegation and web search, ignores ambient rules/config,
and has no API-key fallback, resume or retry path. Unexpected command, route,
scope, mounted-byte or source changes fail closed.

Prospective clarification before outcomes: the restriction is exactly four
repository-access capabilities, not a claim of literally four total model-visible
tools. Identical non-I/O bookkeeping is permissible only if it cannot execute,
browse/history, delegate, access/write external state or mutate resources.
The pinned client's full built-in catalog remains unknown. Command configuration
and observed-event screening do not prove absence of exposed capabilities.
The separately authorized canary must establish configuration support and verify
that no disallowed capability was exposed or used; readiness remains false.
Current [official MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)
documents per-server `enabled_tools`, not the entire pinned built-in catalog.

## Lifecycle and evidence

The existing 20-minute guard starts before attempt preparation. Its signal reaches
the existing contained CLI call; mandatory client/container/sidecar/network cleanup
runs uncancelled. Start and invocation evidence must persist before execution.
Raw/partial output, JSONL, bounded failure diagnostics, nested cleanup failures,
tool audits and terminal usage remain create-only evidence. Unknown token usage
or unproven cleanup stops progression. Original live 120k/16k guarantees remain
unmet; this does not claim equal compute or an exact served model/version.

The structural factory requires an injected executor and cannot mint a
provider-class capability. Deterministic tests exercise real local HTTP readers,
synthetic Docker observations and synthetic CLI results. They do not invoke
Docker or Codex, prove pinned-client support, or constitute a provider canary.
Normal completion is not elapsed-deadline or forced-termination evidence.

new groups cover exact command policy, real four-reader attachment, A/B scope,
one-use/default-deny/cross-run/reseal/mount rejection, deadline propagation,
uncancelled cleanup, retained aggregate failure, disallowed observed capabilities
and invocation-evidence collision with zero CLI invocations. Existing tests were
not weakened. New fixture corrections preserve the reader's explicit native-link
unavailability instead of claiming complete tree/search results.

bindings, validation receipts and a real-mount synthetic-only canary receipt.
Its successor freeze binds the local public commit, transitive runtime source,

`providerAuthorized` and `executionReady` remain false. Actual canary approval,
client/catalog/identity evidence, independent canary review, separate batch
